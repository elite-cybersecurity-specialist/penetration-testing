# Client Confidentiality and Responsible Disclosure

[← Back to main page](../README.md)

**We protect the blueprint.** A client should understand its security architecture and risks without requiring the public release of details that make compromise easier.

## Information Not Shared in This Public Repository

Client names without authorization; live asset inventories; internal architecture secrets; passwords; session tokens; private keys; raw vulnerability evidence; confidential findings; internal firewall policies; network identifiers; recovery procedures; personal data; incident details; and unapproved client screenshots.

## Operational Handling Principles

- **Collect minimally:** Capture only the evidence necessary to establish a finding and remediation result.
- **Restrict access:** Share reports with designated recipients through authorized secure channels.
- **Limit retention:** Agree on retention and deletion requirements in writing before testing.
- **Escalate critical findings:** Use the agreed technical and business contacts promptly.
- **Obtain disclosure approval:** Publish a case study, finding, vulnerability identifier or technical demonstration only through explicit written approval and coordinated disclosure when relevant.
- **Separate research and client environments:** Public R&D materials are not a substitute for customer authorization.

## Public Repository Security

This GitHub repository is a **service information and documentation repository**. Its public availability is not permission to scan or test ECS infrastructure, GitHub accounts, connected services or customers.

If you believe that repository contents accidentally contain a credential or confidential client information, contact **Yuhisern@protonmail.com** directly. Do not post live secrets or private findings in a public issue.
